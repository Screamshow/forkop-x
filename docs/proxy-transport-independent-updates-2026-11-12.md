# Независимые обновления Forkop / Xrust / ZMS

12 ноября 2026, МСК. Продолжение `proxy-transport-zapret-2026-11-12.md`.

## Требование и окончательные правки

Компоненты обновляются пользователем отдельно, порядок не является условием
сохранения маршрутизации. Нет принудительного обновления соседних компонентов,
новых уведомлений, баннеров или обязательной проверки новой версии ядра при
запуске. Полная защита UDP-транспорта требует обновлённого Xrust; промежуточная
совместимость не означает, что старое ядро уже применяет SO_MARK.

- Удалён добавленный ранее отказ генератора для AWG/HY2/MASQUE на старом
  Xrust. Forkop использует прежнее поле routing_mark, принимаемое старым ядром.
  TCP dialers старого Xrust уже применяют это поле; WG/AWG/HY2/MASQUE старого
  ядра могут игнорировать его до обновления core.
- Отсутствующий zapret не устанавливается. Сторонние файлы, сервисы и nft
  таблицы не изменяются на основании имени каталога или наличия nfqws.
- Для изменения zapret необходим наш контракт backend ZMS и подтверждённое
  владение core: квитанция с SHA-256 бинарника и producer-helper. Она создаётся
  только после успешной явной установки соответствующего core через ZMS.
  Обновление панели не создаёт квитанцию для произвольного найденного core.
- Исторические наши ARM пакеты r100 дополнительно распознаются по точным
  хешам файлов, ревизии установленного APK и контракту нашего backend.
  Подмена бинарника/helper после установки прекращает автоматическое владение.
  Ссылки вместо ожидаемых файлов не принимаются.
- Наши guard-поправки нормализуются перед проверкой хеша, поэтому повторный
  prepare узнаёт ту же установку и не теряет защиту из-за собственного изменения.
- Для новых квитанций не нужны новые UI или пользовательские действия сверх
  уже запрошенной установки core. Старый ZMS без квитанций и generic upstream
  core не объявляется нашим только потому, что наша панель стоит рядом.

## Пакетная матрица

Существующая VMware OpenWrt 25.12.5 x86/64, `192.168.1.1`.

| Компонент | Старый | Новый тестовый кандидат |
|---|---|---|
| Forkop backend APK | 2.6.8 | 2.7.2-canary.9912 |
| Xrust APK | 0.0.36-r1 | 0.0.40-r9002 |
| ZMS backend | установленный 4.71.4 | локальный dev с исправлением |

Номера кандидатов непубличные, не заменяют существующие релизные пакеты.
Forkop собран штатным build.sh из dev без чужих незавершённых frontend-правок.
Xrust упакован штатным package_openwrt.py; source base
`91ca73c041c05ffaa8f0715794a5149fcf4f14a5` плюс локальный diff.

Проверены все восемь состояний F/X/Z (0 — старый, 1 — кандидат):

`000 → 100 → 110 → 010 → 011 → 111 → 101 → 001 → 000`.

Forkop и Xrust действительно устанавливались APK-менеджером со штатными
pre/post hooks, включая обратные переходы для обхода матрицы. В части ZMS
этого прохода атомарно заменялся **только backend**, а не выполнялся полный
установщик восемь раз. После каждого шага проверены запуск, перезапуск,
проверка runtime JSON установленным core, DNS, PID из procd и status ZMS.
UCI Forkop сравнивалась без единственного служебного shutdown_correctly;
sing-box UCI — побайтово. Все восемь состояний прошли.

Полный новый установщик панели отдельно проверен:

1. Со старыми Forkop 2.6.8 и Xrust 0.0.36.
2. В реальной последовательности APK Forkop → APK Xrust → полный установщик
   ZMS, с проверкой после каждого шага и финальным restart Forkop.

Оба полных запуска выполнены в существующем режиме `ZM_FORKOP_TRANSACTION=1`:
установка backend, RPC, меню, assets и launchers выполняется, но зависимости
панели не устанавливаются автоматически и её delayed watchdog не запускается.
Не заявляется полный standalone bootstrap на чистой прошивке.
RPC health панели и рабочий Forkop сохранились. Сторонний zapret не устанавливался.

## Трафик и совместимость конфигурации

Дополнительный изолированный IPv4 AWG-стенд: независимый amneziawg-go,
одноразовые ключи, два namespace, реальный nfqws, отдельные копии старого и
нового core под собственными именами. Все адреса confined к namespace.

Восемь проходов с сочетаниями старой/новой маркировки и core дали 16 успешных
HTTP/HTTPS передач: AWG и Direct в каждом проходе. Это повторение четырёх
сочетаний F/X; ZMS в этих сетевых проходах не менял dataplane и его цифра в
метке не является отдельным трафик-тестом установщика.

- Старое ядро и новая конфигурация AWG продолжили передавать payload.
- Старый Forkop и новое ядро также продолжили передавать payload.
- При новом Forkop + новом core очередь не получает защищённые AWG-пакеты.
- При остальных промежуточных сочетаниях обработка AWG в nfqws ещё может
  происходить; это ожидаемое отсутствие полной защиты, не поломка маршрута.
- Direct во всех проходах продолжил попадать в очередь и передавать payload.
- Полная AWG-конфигурация, сформированная новым production-генератором,
  принята установленным старым Xrust 0.0.36 (`check`).
- Реальные AWG IPv6 и TCP/VLESS проверки all-new, а также 12 initial-packet
  HY2/MASQUE проверок — в предыдущем отчёте; здесь они не повторялись.

## Владение и регрессионные тесты

`tests/proxy_transport_ownership_vm.sh` на той же VM подтвердил:

- чужие helper и активные nft-правила побайтово не меняются, даже с контрактом
  нашей панели, если нет подтверждения происхождения core;
- с валидной квитанцией guard устанавливается и повторно применяется;
- внешний mismatch бинарника не принимается как наше обновление;
- отсутствующая установка не создаётся.

`tests/proxy_transport.uc` подтвердил отдельную маркировку Connection/AWG,
сохранение Direct и совместимость поля со старым core. Shell syntax,
proxy-transport, backend-behavior и panel-contract тесты ZMS прошли после
последних правок. `git diff --check` для трёх рабочих копий прошёл.

## Восстановление

Все исходные версии пакетов восстановлены и полный список APK совпал.
Хеши `/etc/config/{forkop,sing-box,network,firewall,dhcp}` совпали. DHCP сначала
отличался только `forkop_dns_transaction_id` после restart; настройки DNS/DHCP
не менялись. Служебный идентификатор восстановлен из копии с точным исходным
хешем после проверки, что других различий нет.

Файлы панели восстановлены из приватного архива, оставшегося только на VM;
исходный backend и uhttpd/system/crontab совпали. RPC и DNS работают.
В ходе package hooks запустился нативный forkop-tailscale по сохранённому
enabled-флагу; до теста работал только штатный tailscaled. Нативная служба
остановлена, исходный штатный tailscaled сохранён, изначальный элемент
forkop-tslan в наборе интерфейсов восстановлен. Статический полный nft ruleset
после этого совпал побайтово. Это побочное поведение уже существующих hooks,
не новая логика изоляции Connection.

Временные процессы/namespaces удалены; блокировки upgrade hold нет.
